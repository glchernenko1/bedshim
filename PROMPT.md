Ты начинаешь проект **bedshim** — офлайн веб-приложение, которое превращает карту
стола Klipper в план подклейки каптонового скотча, печатает эталонную решётку в
STL и замыкает цикл калибровки.

## Шаг 0 — до любой работы

1. **Попроси у меня ссылку на GitHub-репозиторий.** Я создал (или создам) пустой
   репозиторий и вставлю ссылку. Пока ссылки нет — не начинай код, но можешь
   читать документы и задавать вопросы.
   Вопрос должен звучать так:

   > «Дай ссылку на пустой GitHub-репозиторий для bedshim (например
   > `https://github.com/<you>/bedshim.git`). Если репозиторий ещё не создан —
   > создай пустой, без README и без .gitignore, и пришли ссылку.»

2. Получив ссылку:
   - если в папке нет `.git` — `git init -b main`;
   - `.gitignore` → `node_modules/`, `dist/`, `.DS_Store`, `*.local`, `.codegraph/`;
   - `git remote add origin <ссылка>`;
   - первый коммит `chore: scaffold bedshim` с `SPEC.md` и `PROMPT.md`;
   - **пуш — только после моего подтверждения.** Спроси отдельно.

3. **Прочитай `SPEC.md` целиком.** Это контракт, а не пожелание. Если строчка
   неоднозначна или кажется физически неверной — **стоп, спроси**, не выбирай
   удобную трактовку.

## Шаг 1 — инструменты (обязательно)

- **CodeGraph.** Инициализируй индекс в корне проекта (`codegraph init`) и дальше
  пользуйся им **вместо** grep/чтения файлов, когда нужно понять или найти код:
  `codegraph explore "<символы или вопрос>"` или MCP-инструмент codegraph, если
  он доступен. Оптимизируй индекс после крупных изменений структуры, не после
  каждой правки.
- **Context7.** Для документации библиотек — React, Vite, Ant Design 5, zustand,
  Vitest, `polygon-clipping`, `earcut`. Не пиши API по памяти: сначала
  `resolve-library-id`, потом запрос доков по одной теме.
- **gh_grep.** Когда нужен реальный пример использования (STL-писатели,
  триангуляция полигона с дырками, паттерны Ant) — ищи код, а не статьи.
- Если инструмент недоступен — скажи об этом и продолжай без него, не
  подменяй молча.

## Шаг 2 — стек и правила

TypeScript + Vite + React + Ant Design 5. Больше ничего без моего согласия.

Жёсткие правила из `SPEC.md`, которые легко нарушить по невнимательности:

- **`src/core/` — headless.** Ни React, ни DOM, ни `window`. Запускается в Node,
  покрыт Vitest. Это единственная часть, которая переживёт смену UI.
- **Никакого бэкенда, CDN и внешних шрифтов.** `base: './'` в Vite. Приложение
  должно открываться офлайн и без изменений вставляться в webview Orca.
- **i18n обязателен:** EN по умолчанию, RU переключателем, все строки — включая
  сгенерированные инструкции и предупреждения — через `t('key')`. Код, имена,
  комментарии и коммиты — на английском.
- **Физику не менять «чтобы числа были красивее».** §1 SPEC (только добавление,
  мостинг/σ, сжатие, мёртвая зона) — не декорация.
- **`floor`, а не `round`, пока материал не откалиброван.** Перебор скотча
  необратим, недобор — нет.
- **`buildGrid` — единственный источник геометрии клеток.** Планировщик, STL и
  SVG берут клетки только оттуда.
- Никакого G-code в v1. Никакого мультиматериала в v1.

## Шаг 4 — определение готовности

Фаза готова, когда:

1. `npm run test` зелёный, новые функции покрыты тестами;
2. фикстура из Appendix A проходит как golden-тест;
3. `npm run build` проходит, `dist/` открывается офлайн;
4. в отчёте: что сделано, что проверено, где отступил от спеки и почему;
5. нет `any` в `src/core`, нет `eslint-disable` без объяснения.

## Шаг 5 — когда спрашивать, а не решать

Спрашивай, если:

- спека противоречит физике или самой себе;
- нужно добавить зависимость;
- нужно изменить §1 SPEC;
- нужно поменять публичные типы `src/core`;
- предстоит пуш в remote, force-push, удаление файлов.

Всё остальное внутри фазы решай сам и пиши, что решил.
